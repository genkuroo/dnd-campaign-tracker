# Build log — D&D campaign tracker

Detailed phase-by-phase build history, subsystem deep-dives, and future-idea
blueprints. This is the **archive** that used to live inline in `CLAUDE.md`;
it was split out to keep `CLAUDE.md` focused on the conceptual model + current
state. Read `CLAUDE.md` first for the two spines and conventions; come here for
"how exactly was X built / which migration / which model file."

Everything below is **done unless marked otherwise**. Phases are ordered by the
"local single-user first → auth → hosting → ambitious visuals last" arc. The
recurring implementation patterns (computed-on-read, snapshot-on-add, AJAX
fragment re-render, guided-not-enforced, edit-gating) are summarized in
`CLAUDE.md § Recurring patterns`.

## Phases 0–6 (local single-user core)

**Phase 0 — Scaffold & shell.** Flask app (`app.py`, port 5002), SQLite bootstrap (`db.py`, `meta`/schema-version table), base layout with the tab navigation shell (Character / Spells & Actions / Map / Blog) + entity sidebar placeholder. No real data yet.

**Tab split (later, Phase 7 cleanup):** the **Character Sheet** tab became "your character" — a player lands directly on their own PC's sheet (DM sees the PC roster); **NPCs moved to their own tab** where the DM manages the cast and players see the NPCs they've **encountered** (revealed = `visibility='visible'`). `can_view_creature` lets players read-only view any non-hidden PC **or** NPC.

**Phase 1 — Creature engine + character sheets.** Six ability scores + modifiers (`floor((score-10)/2)`), HP, AC, resistances/immunities/vulnerabilities. Shared `creatures` table (migration 1) with `kind` ('pc'|'monster') and the `visibility` field ('visible'|'hidden'). `models/creature.py` owns the stat-block math + CRUD; Character Sheet tab does list/view/create/edit/delete. DM-only, local — player enforcement of `visibility` waited for Phase 7.

**Phase 2 — Dice roller.** `models/dice.py`: `parse_and_roll` is the single entry point — it dispatches an optional adv/dis suffix (`d20 adv`, `d20+3 dis`) to `roll_check`, else parses an expression (`2d6+3`, `1d20+1d4-1`, bounds-guarded). Dice tab uses a **confirm-before-roll** flow: quick buttons (d4–d100, adv/dis) only *populate* the expression box via JS (dice append, adv/dis replace); nothing rolls until the Roll button. Persisted log = migration 3 `rolls` table + `models/roll_log.py`; each entry shows a local-time stamp (relative time on hover), and a >5-min pause (`ROLL_GAP_SECONDS`) draws a divider grouping rolls into bursts (`_decorate_rolls`). Wired to the sheet: a per-ability **Check** button rolls `d20 + modifier`, logs it, flashes in place (`next` returns to the sheet; `_safe_next` blocks open redirects).

**App-wide AJAX rolling + in-place sheet mutations (no migration).** Two UX passes so the character sheet stops doing full-page reloads. **(1) Every dice roll is AJAX:** `dice_roll` returns **JSON** (total/detail/label/roller color) when called with `X-Requested-With: fetch` (else the old flash+redirect for the Dice page, which opts out via `data-no-ajax`); a single app-wide handler in `base.html` intercepts any `.rollable` die-click *or* any form POSTing to the dice engine (Check/Save/Skill/Cast/spell-Attack/weapon-Attack/Damage/Crit) and shows the result in a floating **roll toast** (`#roll-toast`, tinted by the roller's colour). The sheet's fragment boxes (`#gear`/`#spells`/`#actions`/`#feats`) gain an `isDiceForm` guard so a roll form inside them **bubbles past** to the app-wide roller instead of being swallowed by the fragment handler; the adv/dis capture handler still adjusts the expression first. **(2) State mutations re-render the sheet in place:** the whole sheet is wrapped in `<div id="sheet">` and the per-section JS init is factored into a re-callable `initSheet()`. A `js-sheet-reload` form (**Exhaustion ±, Inspiration grant/use, Level-up, ASI ±**) submits via fetch (following the server's redirect to the GET sheet), extracts the fresh `#sheet`, swaps it, and re-runs `initSheet()`.

**Phase 3 — Spells/abilities + SRD rules reference.**
- **3a — Spell reference + Assist/Track mode.** SRD spells bundled locally (`data/spells.json`, CC-BY-4.0; `models/spells.py`). Spells & Actions tab: library with **client-side search + filters** (type: Cantrips/Spells; casting time: Action/Bonus/Reaction) → spell detail. A site-wide **Assist/Track** toggle (cookie, default `track`, top bar): in **assist** mode dice in rules text are clickable (`dicetext` filter → `.rollable` → base-layout JS posts to the dice engine) and a **Cast** button rolls the spell; in **track** mode dice are reference-only and casting is hidden. Mode is a personal UI pref — cookie is fine pre-auth.
- **3a.1 — Glossary tooltips.** Reusable `info(key, display)` macro (`templates/macros.html`) renders an ⓘ with a hover/focus tooltip from `models/glossary.py` (`define` is a Jinja global so imported macros can reach it). Drop `{{ info('term', 'Label') }}` next to any jargon, anywhere; unknown terms render plain.
- **3b — Character spellbooks.** `creature_spells` join (migration 4, slug + `prepared`, ON DELETE CASCADE) + `models/spellbook.py`. Character sheet shows known spells (prepared toggle, mode-aware rollable, remove); spells addable from both the sheet and the spell page. Shared `/spellbook/{add,remove,prepared}` routes keyed by form `creature_id`+`slug`+`next`.

**Phase 4 — Inventory, loot, currency, XP/leveling.** Migration 5 adds `xp`/`gold`/`silver`/`copper`; `models/creature.py` has the 5e XP table (`level_from_xp`, `xp_to_next`) — level stays manual (milestone-friendly) with XP-based level-up hints. Migration 6 + `models/inventory.py`: per-creature `creature_items` (name, quantity, description, equipped). Sheet shows a coin purse, XP progress, and an Inventory section. **Equipment slots** (migration 7, `slot`+`hands`): fixed slot set (main/off hand, armor, helmet, cloak, gloves, boots, amulet, rings×2); `equip_item` enforces one-per-slot by swapping, and the two-handed rule. Sheet has a BG3-style slot panel (`equipped_by_slot`) with **drag-and-drop equip** (HTML5 DnD; slot-match client-side, equip/swap server-side via `/inventory/<id>/equip`).
- **4c — DM loot system.** Items are no longer created on the sheet; acquisition flows through loot. **Loot tab** + `areas`/`loot_items` tables (migration 8), `data/items.json` premade catalog (`models/items.py`), `models/loot.py`. Each **area** (current one tracked in `meta.current_area_id`) has its own loot pool; the DM **spawns premade** or **creates custom** items, then **gives** to a roster member (copies into `creature_items`). Loot is distributed to PCs only; NPCs are stocked manually via an add-item form on NPC sheets. Areas are a lightweight precursor to the Phase 9–10 location system.
- **Inventory UX:** equipment slot panel is a **BG3-style paper doll** (`SLOT_COLUMN`), side by side with the inventory (`gear-layout`). Inventory is a **fixed-height scrollable panel** (JS-synced height) with its own **name search + All/Equipped/Equippable filter** (state kept outside the `#gear` fragment so it survives AJAX re-renders). Two distinct ring boxes (`equipment_panel` expands one cap-2 `ring` slot). Each filled slot has an **unequip ×**. Gear actions are **AJAX** (re-render `#gear`/`_gear.html`; delegated handlers survive replacement; non-JS falls back to POST+redirect). Characters tab has a name search + PC/NPC filter with color-coded kind badges.

**Phase 5 — Monsters, inspector, encounters.**
- **5a — Actions/Abilities system.** A **separate, creature-attached** action system, kept *distinct* from spells: spells are SRD-backed with level/components; actions/abilities (Multiattack, Rage, breath weapons, legendary actions, passive traits) are free-form. Migration 9 `creature_actions` (name, `category` trait|action|bonus|reaction|legendary, optional `dice`, description) + `models/actions.py`. Sheet shows an **Actions & Abilities** section grouped by category, mode-aware rollable dice. Works for PCs/NPCs/monsters with no special-casing. **Mostly *grabbed from a list*, not authored:** an **action book** catalog (`data/actions.json`, `models/action_catalog.py`) is the primary add path (category-grouped dropdown), also surfaced in the Spells & Actions tab behind a Spells/Action Book toggle. Grabbing copies the entry onto the creature; a secondary "custom action" form allows one-offs. Shared `/actions/add` + `/actions/<id>/remove`.
- **5b — Bestiary + read-only inspector.** Monsters reuse the creature engine wholesale: `kind='monster'`, same `character_detail` view, create/edit/delete through the shared character routes. **Bestiary tab** (`list_monsters`, name search, create) and the **BG3-style read-only inspector** (`/bestiary/<id>/inspect`). Migration 10 adds `stats_revealed` (distinct from `visibility`): the inspector **masks the stat-block numbers** until the DM flips the reveal live (`/bestiary/<id>/reveal`).
- **SRD monster catalog (post-launch, 2026-06-10).** A bundled `data/monsters.json` (~65 iconic SRD 5.1 monsters, CR 0–10 — humanoids, beasts, undead, fiends, giants, and several dragons incl. a young red dragon, CC-BY-4.0) + `models/monster_catalog.py`. The Bestiary gained a DM **"📥 Add SRD monsters"** button (`bestiary_import`, DM-only) that bulk-imports the catalog — reusing the "catalog → grab" pattern (like loot/action-book/summons): each entry's stat block is copied into a new `kind='monster'` creature and its actions attached via `add_action`. **Idempotent** (skips monsters already present by name, so re-running after catalog updates is safe) and imported monsters default **`visibility='hidden'`** (the DM's library; reveal each per the level-1 monster fog of war). Senses / condition immunities / extra movement that have no column are summarized in each monster's `notes`. Avoids hand-entering common monsters and never touches the prod DB directly — the DM just clicks the button on the live site.
- **5c — Encounters.** Saved **named groups of monsters**. Migration 11 `encounters` + `encounter_members` (creature_id + quantity, so 'Goblin ×4' is one row) + `models/encounters.py`. On the Bestiary tab with an encounter detail page: add monsters, quantity ±, remove, rename, delete.

**Phase 6 — Combat tracker.** Migration 13 (`combats` + `combatants`) + `models/combat.py`. A **Combat tab** runs a live fight on the creature engine — PCs and monsters in one tracker. Combatants **snapshot their own HP/AC** when added (not the creature), so multiple instances of one stat block take damage independently. Build a fight by adding roster members or **loading a saved encounter** (also a "⚔️ Start combat" button on the encounter page). Features: per-combatant **initiative** (manual or `🎲 Roll initiative` = d20+DEX for all), **initiative order** with active turn highlighted; **▶ Next turn** (`turn_combatant_id`, robust to add/remove) and round bump on wrap; **damage/heal** (temp-HP absorbs first, heal capped at max) with a %-coloured HP bar; **temp HP** (set, not stacked); **conditions** (14 SRD conditions as chips); short/long rest. Tracker actions are **AJAX** (`#combat` fragment; no-JS falls back to POST→redirect). **Combat history** (migration 14 `status`): "End combat" *archives* to a History list. **Initiative is one-time** (`initiative_rolled`). **Rests moved to a new Party tab** (downtime, not a fight): party-wide long rest / short rest (≈ half each PC's missing HP, hit dice untracked) + per-PC damage/heal, on the real sheets. Party HP-adjust + rests are **DM-only** (`is_dm()` — route 403 + UI hidden).

## Phase 7 — Accounts, roles & the visibility spine (enforced)

The leap to a true multi-user web app.

- **7a — Auth foundation.** Migration 15 `users` (role 'dm'|'player', `creature_id` PC link, `color` for 7d); `models/user.py` with **werkzeug-hashed** passwords. **Real passwords, shared signup code** model: first run with no users forces a **`/setup`** page to create the DM; the DM sets a **signup code** (in `meta`) on the **Users tab**, players self-register at **`/register`** with that code. `/login`, `/logout`, session-based; a `before_request` gate redirects anonymous visitors to login (public endpoints: login/logout/register/setup/static). `is_dm()` is now **real** (`current_user()` + role). `current_user`/`is_dm` injected into every template. DM Users admin: set/clear signup code, assign each player to a PC, reset password, delete (can't delete self).
- **7b — Player ↔ character.** The DM **assigns/unassigns** players ↔ PCs on the Users tab. A player with no character gets a "Create my character" prompt (`/character/create-mine`) that creates a PC (forced kind=pc, visible) and **auto-assigns** it; once they have one they can't create a second.
- **7c — Visibility enforcement (core).** Server-side fog-of-war. `can_view_creature` / `can_edit_creature` + a `before_request` block of the whole DM-authoring surface (`_DM_ONLY_ENDPOINTS`: bestiary, encounters, combat, loot, party, users, create/delete character). A **player edits only their own PC** (edit/levelup/avatar/disposition/inventory/spellbook/actions → 403 on others) and can **read-only inspect fellow party members** (own PC or any non-hidden PC; NPCs/monsters 404). The Party tab lists viewable party members → **read-only sheet** (controls gated by a `can_edit` flag threaded through the sheet + `_gear`/`_spells`/`_actions`; **Notes private** to owner+DM; DM's `visibility='hidden'` hides a PC from the party). Spell library "Viewing as" + add-to dropdowns scoped to the viewer.
- **7d — Per-player roll colors.** Migration 16 adds `rolls.user_id` (ON DELETE SET NULL); `dice_roll` records the roller and `recent_rolls` joins name + `users.color`, so the shared dice log **tints each roll**. Each user sets their own colour on the Dice page (`/me/color`); DM can set anyone's. Colours validated server-side as hex. Rolls stay server-authoritative.
- **7e — Player read-only Combat + Party.** `party`/`combat`/`combat_detail` views are no longer DM-only, so players can open them; every **mutation** stays DM-only (403). Combat renders **read-only for players** (controls wrapped in `{% if is_dm %}`; players see static initiative + "watching — your DM runs the fight" + read-only condition chips). **Loot tab is now shared:** players see the current location's loot pool and can **Take** items to their PC (`loot_take`, current area only) and **Drop** own items into it (`loot_drop` + `drop_to_loot`). **Currency loot:** a loot item can carry coins (migration 18 `gold`/`silver`/`copper` on `loot_items`; premade currency in `items.json`; "Drop coins" form) — taking/giving adds to the PC's **purse** (`is_currency` / `give_loot`). Sheet purse has a direct **± Adjust** (`character_coins` → `adjust_coins`, clamped ≥ 0, owner/DM only).

**Bestiary player fog of war** (`can_inspect_monster`): **level 1** = DM toggles each monster's `visibility` (players' bestiary lists only visible monsters, 404 on hidden); **level 2** = DM toggles `stats_revealed` from the inspector (visible-but-unrevealed shows a masked card 🔒 + masked inspector). Players get the **inspector only**; the full monster sheet stays DM-only.

**Open question (7c, still open):** spellbook/ability/inventory visibility — *creature-level* (a hidden creature hides its whole stat block, current default) vs optional *per-entry reveal* (add a `visibility` column to `creature_spells`/items). Deferred.

### Magic items (migrations 19–22)

An equipped item can grant an **AC bonus**, **ability-score bonuses** (`stat_bonuses`, `ability:amount` pairs), and/or **spells** (`grants_spells` slugs). Applied by **computing** the creature's *effective* AC / abilities / spell list from equipped items (`effective_ac`, `effective_abilities`, `effective_spells`) — the base sheet is never mutated, so bonuses revert on unequip/remove. Sheet shows effective values with a `+N` tag; item-granted spells flagged "from <item>". Combat snapshots effective AC + DEX.

**Body armor (migration 21)** follows 5e: `armor_type` (light/medium/heavy) + `armor_base` **set** the AC and cap DEX (light = full, medium = +2, heavy = none); `effective_ac` uses worn armor base + capped DEX; an **unarmored PC** is `10 + DEX` with optional **Unarmored Defense** (migration 22 `unarmored_defense`: barbarian +CON, monk +WIS); **NPCs/monsters keep manual natural AC**; additive `ac_bonus` (shield/ring) stacks on top. (Armor with no base AC is ignored.) AC shows everywhere via the `eff_ac` filter with an `ac_breakdown` tooltip. DM item-creation forms (loot create + NPC gear) get a `magic_fields()` section; premade magic items in `items.json` (Shield +2 AC, Cloak/Ring of Protection +1, Amulet of Health CON+2, Belt of Giant Strength STR+2, Wand of Fire Bolt). Bonuses carry through loot give/take/drop.

### Class system (the bones, migration 23)

`data/classes.json` + `models/classes.py` define the 12 SRD classes (hit die, primary/save abilities, Unarmored Defense, spell ability, recommended stat array, starting equipment, gold). A creature records `class_name`. Picking a class applies a **BG3-style starting kit** (`_apply_class` with `starting_kit`): recommended stats, **level-1 HP from hit die + CON**, starting gold, **auto-equipped starting gear** (feeds the AC/armor system), Unarmored Defense (barbarian/monk). Player self-create always applies the kit; the DM form has an "Apply starting kit" checkbox. **Leveling:** the level-up control pre-fills HP with the **fixed hit-die average + CON** (`hit_die_average`); class shows on the sheet. Each class carries `skill_count` + allowed `skills` (drives the guided skill picker) and a per-level `features` list.

**Class features (display layer).** Every class has a `features` list of `{level, name, description}` — SRD class features L1–20 (with ASI markers and a generic subclass marker). `class_features(slug, level)` (unlocked through level) and `class_features_remaining(slug, level)` ("Coming up" preview) — both **computed on read**. The sheet renders a **"<Class> Features"** section (between Skills and gear, only for classed creatures) + a collapsible "Coming up".

**Auto-granted class actions (migration 26).** Action-type features tagged with a `category` (+ optional `dice`) in `classes.json` (Rage, Second Wind, Sneak Attack, Channel Divinity, Cunning Action…) are **auto-granted into the creature's actions list**. `creature_actions` gained a `source` column ('' = hand-added/grabbed, 'class' = auto-granted). `models/actions.grant_class_actions(creature_id, slug, level)` **reconciles** (not wipes): keep still-desired ones (preserving `hidden` + edits), drop no-longer-granted, add newly unlocked — idempotent, leaves hand-added untouched. App helper `_sync_class_actions(creature_id)` runs after **class apply**, **edit**, and **level-up**. Granted actions show a gold **"class"** tag and carry a **Hide** control instead of **×** (a real delete would re-sync back).

**Hide / Show hidden on filterable lists (migration 27).** Spells, actions, and inventory each gained a per-entry **Hide** toggle and a **"Show hidden (N)"** button — a persistent soft-delete / declutter. `hidden` columns; setters `set_spell_hidden`/`set_action_hidden`/`set_item_hidden`; routes `/spellbook/hidden`, `/actions/<id>/hidden`, `/inventory/<id>/hidden` (edit-gated, AJAX-rerender). The client filter JS adds a `showHidden` predicate (default off). Also the **permanent way to remove an auto-granted class action** (the reconcile preserves `hidden`). (Item-granted spells, having no DB row, can't be hidden.)

### Proficiency layer (migration 24)

The trained-bonus system on saves and skills (`models/proficiency.py`). `creature.proficiency_bonus(level)` = `2 + (level-1)//4`. **Saving throws:** proficiency *derived from class* (each grants two, in `classes.json`'s `saves`) — no per-creature storage; `save_table` returns each save modifier. **Skill checks:** 18 SRD skills (`SKILLS`, slug→ability) with per-creature proficiency in the `creature_skills` join (set on the form's **DM-only** "Skill Proficiencies" picker via `set_skill_proficiencies`); `skill_table` returns each modifier. **Skills are DM-controlled** (picker hidden from players, setter gated by `is_dm()`). Both **computed on read**. Sheet's ability grid gains a **Save** button + a **Skills** section with Roll buttons, all posting `d20 + (modifier incl. prof)` through the dice engine (`signed` filter). The skill picker is **guided (not enforced)**: class `skill_count` + allowed `skills`, inline JS highlights class skills + live "X of N" budget; off-list picks still work.

### Spellcasting (migration 25, `models/spellcasting.py`)

Two computed layers on the spellbook. **Stats:** **spell attack bonus** (`prof + ability mod`) and **save DC** (`8 + prof + ability mod`), ability = class's `spell_ability` — computed on read. **Slots:** leveled spells spend a slot of their level (cantrips free); *max* slots come from **caster type** (`caster_type` in `classes.json`: `full` Bard/Cleric/Druid/Sorcerer/Wizard, `half` Paladin/Ranger, `pact` Warlock, `none`) + level via the 5e tables (`_FULL`/`_HALF`/`_PACT`); only *expended* slots stored (`creature_spell_slots`). A **long rest** clears all slots, a **short rest** recharges only Warlock pact slots — wired into Party-tab rests and per-caster sheet rest buttons. The spell section has a **Spellcasting panel** (ability · attack · DC + slot tracker with pip display and ±/spend/restore); each spell line gains an **Attack** roll, a **DC** badge, and a **Cast ▸** that spends a slot. Mutations edit-gated (`/spellbook/slot`, `/spellbook/rest`), AJAX `#spells` re-render.

## Class system depth (roadmap, mostly done)

Fills in the mechanics that make a class feel complete; layers on computed-on-read + reconcile patterns.

- **Subclasses (migration 28).** Each class records a `subclass` slug; `classes.json` carries `subclass_level` + `subclass_label` (Primal Path, Divine Domain…) and a `subclasses` list, each with its own level-keyed `features` (one SRD archetype per class). `class_features`/`class_features_remaining`/`grantable_class_features` take an optional `subclass` and **merge** subclass features (sorted by level, tagged `subclass`); action-type subclass entries (Cutting Words, Preserve Life, Fast Hands…) auto-grant via `grant_class_actions`. The form gains a subclass `<select>` (filtered via JS); server validates the pick. Changing class clears an incompatible subclass.
- **Class resources (migration 29, `models/resources.py`).** Limited-use, rest-recharged pools — the non-spell cousin of the slot tracker. Each class carries a `resources` list in `classes.json` (Rage, Ki, Channel Divinity, Lay on Hands, Action Surge/Second Wind/Indomitable, Wild Shape, Bardic Inspiration, Sorcery Points, Divine Sense), each with a computed `max` (`fixed`/`level`/`level_times`/`steps`(-1=∞)/`ability_mod`), optional `min_level`, and a `recharge` (`short`=short or long; `long`=long only; optional `short_from_level`). **Max computed on read; only expended stored** (`creature_resources`). `resource_rows` builds display; `spend_resource`/`restore_resource` (amount-aware); `rest(creature, kind)` clears matching keys. Sheet has a **Class Resources panel** (`_resources.html`, `#resources`) — pips for small pools, numeric `available/total` for HP/point pools, ∞ for unlimited — with −/+ and Short/Long rest. Rests recharge **resources *and* slots** together (the spellcasting panel hides its own rests when a resources panel is present, `has_resources`). Wired into Party-tab rests too. Edit-gated.
- **Scaling feature numbers.** A feature can carry a `scale` spec that recomputes `dice` by level: `dice_count` (Sneak Attack = ceil(level/2)d6; Divine Strike via steps), `die_steps` (Martial Arts 1d4→1d10; Bardic Inspiration / Cutting Words 1d6→1d12), `dice_plus_level` (Second Wind 1d10+level). `_scaled_dice`/`_apply_scaling` apply it in `class_features` (computed on read); `grant_class_actions` **rescales the dice on kept class actions** during reconcile (preserving `hidden`).
- **ASI / feats (migration 30, `models/asi.py`).** The +2/+1 bumps a class grants at ASI levels (4/8/12/16/19, + Fighter 6/14 & Rogue 10). **Budget computed on read** (`asi_slots` × 2 points); only the **allocation** stored (`creature_asi`). **`effective_abilities` folds the bumps in on read** (alongside item + race), so AC/mods/saves/skills/spell DC all ripple (`_ability_with_items`). Sheet shows an **Ability Score Improvements** panel (`_asi.html`) with a per-ability −/+ stepper and a live "N of M points left" budget; `+` disables at 0 remaining or base+ASI of 20. `/asi/adjust` is a **full redirect** (touches numbers all over the sheet). `effective_abilities` returns `{score, bonus(items), asi, race, base}`. *Still future: hard validation that base+ASI ≤ 20 against a DM manually raising the base after allocating.*
  - **Feats (skeleton — migration 31, `models/feats.py`).** Tracked list per creature (**display only, no mechanics yet**). Mirrors the action book: catalog (`data/feats.json`) grabbed onto the creature (`creature_feats`: name/description/prerequisite) + custom-add; AJAX `#feats` fragment, edit-gated. **Feats** section on the sheet; ASI panel links to it. **Licensing:** only **Grappler** is SRD (attributed); the rest carry **original paraphrased** one-line summaries (mechanics aren't copyrightable; the PHB itself isn't redistributable). *Still future: linking a feat to the ASI budget, applying feat mechanics.*
- **Spells known / prepared limits (no migration — computed).** Per-class caps on the Spellcasting panel. Two models via `prepared_caster` in `classes.json`: **known casters** (Bard/Sorcerer/Ranger/Warlock) have a `spells_known` table; **prepared casters** (Cleric/Druid/Wizard/Paladin) compute prepared = spell-ability mod + caster level (full) or half (Paladin), min 1. Every caster has a `cantrips_known` cap. `spell_limits(creature, eff_abilities)` returns `{mode, cantrips, leveled}`, counting from the creature's **own spellbook** (item-granted don't count). Renders **Cantrips N/M** and **Known/Prepared N/M** with an amber "over limit" flag. **Guided, not enforced.**
- **Weapon & armor proficiency (no migration — computed).** Per-class `armor_prof` + `weapon_prof` in `classes.json`. `models/proficiency.py` exposes `armor_proficiencies`/`weapon_proficiencies`/`proficiency_summary` (a **Proficiencies** section after Skills) and **`armor_proficiency_issue(creature)`** — the **"Wizard in plate" rule**: a classed creature wearing non-proficient body armor flags **⚠ not proficient** beside AC and a red **"Can't cast"** block in the Spellcasting panel. **Guided, not enforced** (only body armor auto-checked; shields have no reliable item flag). Also: an unprepared *leveled* spell's badge shows **red** (clearer "can't cast now"); cantrips stay neutral.
- **Expertise / half-proficiency (migration 32).** **Expertise** = double proficiency on a chosen *proficient* skill (Rogue/Bard). Stored as an `expertise` flag on `creature_skills`; `expertise_skills`/`set_skill_proficiencies(creature_id, slugs, expertise_slugs)`. The DM picker gained a per-skill **✦ exp** checkbox (JS-gated to proficient skills). **Half-proficiency** computed from features via `_has_feature`: **Jack of All Trades** (Bard 2+, half PB rounded down to non-proficient), **Remarkable Athlete** (Champion 7+, half PB rounded up to non-proficient STR/DEX/CON). `skill_table` returns a `tier` ('expertise'|'proficient'|'half'|None) and the right bonus (2×PB / PB / half PB); sheet shows tier dots (◉ ● ◐ ○). Glossary: `expertise`, `half-proficiency`.

## Magic items & combat depth (roadmap, done)

A 5e-fundamentals review found gaps in magic-item *balance* and in *applying stored data during combat*. Reuses computed-on-read + snapshot-on-add. All **guided, not enforced** unless noted.

- **Attunement (migration 41).** 5e's soft cap: a creature attunes to at most **3** items, only items flagged **Requires Attunement** count. `attunement_required` is a real flag (on `items.json` + `loot_items`/`creature_items`, carried through give/take/drop); `attuned` is a per-item toggle. **Strict mode:** an attunement-requiring item's bonuses apply **only when attuned** — `equipped_ac_bonus`/`equipped_stat_bonuses`/`equipped_granted_spells` gain `AND (attunement_required = 0 OR attuned = 1)` (shared `_ATTUNED_OK`); magic armor's base AC still works (that's `armor_base`). `set_attuned`/`attunement_summary`. ## Phase 8 — Hosting / deployment

Live on **Fly.io** at `https://dnd-campaign-tracker.fly.dev` (region `sjc`). Served by **gunicorn** (`--preload`, 2 workers) in a Docker container; one machine + a **persistent volume** at `/data` (encrypted, daily snapshots) holding the campaign DBs + uploaded avatars (`static/avatars` symlinks onto it). `secret_key` from the `SECRET_KEY` env (`fly secrets`); `init_db()` runs at import so migrations apply on every boot; `PRAGMA busy_timeout` for multi-worker SQLite. `DND_DATA_DIR=/data` selects multi-campaign mode. Redeploy = `fly deploy`. (Cloudflare/AWS-serverless siblings were a poor fit — ephemeral FS, no long-lived process — so Fly's "one VM + a volume" was chosen.) See README for deploy/backup commands.

**Multiple campaigns ("saves").** Each campaign is its own SQLite file under `campaigns/`; a `registry.db` lists them and an `active_campaign` pointer file names the active one (`db.get_connection()` resolves the **active** campaign per request). The DM toggles the active campaign from the **Campaigns** page (📖 chip in the topbar) — **global** switch. **Duplicate** = a point-in-time file copy. `models/campaigns.py` = list/create/rename/duplicate/delete/switch; a legacy single `campaign.db` is **auto-adopted** as the first campaign; every campaign migrated to current schema on boot. `DND_DB_PATH` forces single-DB/test mode. **Accounts live inside each campaign DB**, so new campaigns **seed the DM's account** and the **session is keyed by username** (ids aren't stable across DBs). DM-only. *Still future: cross-campaign shared identity.*

- **9b — Campaign journal (notes, not a blog feed).** A **two-level journal with a DM side and a player side**. Migration 46: `journal_folders` (owner_id, title, description) → `journal_notes` (folder_id, owner_id, title, body, `visibility` private|shared, created/updated; both FKs CASCADE). `models/journal.py` = plain CRUD; **permission logic in the app** (`can_view_note`/`can_edit_note`/`can_view_folder`/`can_edit_folder`). **Decided:** a note is visible to its **owner**, the **DM** (omniscient), and — when **shared** — the **whole party + DM**; a folder surfaces when the viewer owns it or it holds a visible note. **Both DM and players author.** The Blog tab is renamed **"Journal"**; home splits folders into **Mine** + **Players' journals / Shared by the party**. The note form has a **mention picker** (scoped to what the author can see; `_form_mentions` re-checks the allowlist); the note detail shows a **"Featuring"** chip row, and each entity's detail page shows a **"Mentioned in"** back-ref. - **9c — Quest / objective log (migration 48).** `quests` (title, description, `status` active|completed|failed, `visibility` — DM-authored, **default hidden**) + `quest_objectives` (description, `status` open|done|failed, own `visibility`, `position`; CASCADE). `models/quests.py`. **Quests tab** (grouped Active/Completed/Failed) → detail. **Two-level fog of war:** players see only `visible` quests (hidden → 404), and within a visible quest only its `visible` objectives — a **secret objective** inside a known quest stays hidden, and the `done/total` tag counts only what the viewer sees (`_visible_objectives`). DM gets inline objective controls + an add form with a "secret" checkbox; quest-level status + Reveal/Hide + edit/delete. Mutations DM-only. *Future: objective reordering, quest↔entity mentions, due/priority.*

## Phase 10 — Maps

Global + local maps with image backgrounds, position + interactable **overlay markers**, per-player visibility on markers. Most technically ambitious; intentionally last. (Creatures already carry an **`avatar`** — emoji or uploaded image, migration 12, rendered via `avatar()` — meant to double as the map marker.)

- **10a — Map model + image upload + DM view (migration 49).** `maps` table (name, uploaded `image`, `description`, optional `location_id` link 0=none, `visibility` — **default hidden**) + `models/maps.py` (CRUD mirroring `locations.py`; `image` written only via `set_map_image`). - **10b — Markers (overlay + placement) + 10c fog (migration 50).** `map_markers` table (`map_id` CASCADE, fractional `x`/`y` 0..1, `visibility`, polymorphic `entity_type` 'creature'|'location'|'faction'|'map'|'' + `entity_id`, free-text `label`/`icon`) + `models/map_markers.py` (CRUD + `move_marker` clamping, `set_marker_visibility`; `_clean` validates type, zeroes entity_id for free-label pins). **Interactive overlay:** an absolutely-positioned `.map-markers` layer over the image (`.map-canvas` shrink-wraps so percent coords align at any width). **DM:** a **➕ Place marker** button → placement mode (crosshair; markers `pointer-events:none` so the click reaches the canvas) → click drops a pin and reveals `#markerForm` with x/y pre-filled → pick a target (roster NPC/PC, location, faction, or another map — one select per type, JS shows/enables the active one; all default-`disabled` so a JS-less submit degrades to a label pin) + optional emoji icon; **drag a pin** to reposition (→ `fetch` POST to `marker_move`, 204, no reload); a **Markers management list** gives per-marker Reveal/Hide + Delete + Open. Marker mutations DM-only.
- **10d — Display scaling + zoom/pan + grid (migration 56).** Three view upgrades, all keeping the fractional-coordinate marker model intact (pins read the **live** image box via `getBoundingClientRect`, so placement + drag stay correct under any transform).
  - **Fill-width scaling.** `.map-image` is now `width: 100%` (was `max-width: 100%` with no width), so **every map renders at the same on-screen scale regardless of source resolution** — a 100×100 and a 1900×1900 both fill the canvas (small ones upscale soft, large ones shrink crisp), and the fixed-size marker pins read consistently. Previously a small image rendered tiny (never upscaled) and pins dwarfed it.
  - **Zoom & pan (per-view, not persisted).** The DOM gained a `.map-canvas` clipping **window** around a transformed `.map-viewport` (image + grid + markers). A JS engine applies `translate(tx,ty) scale(s)` (transform-origin 0,0; `s` clamped 1–8): wheel-zoom anchored to the cursor, +/−/reset buttons (with a live % readout), drag-to-pan on the background (clamped so the image keeps covering the window; only active when zoomed in). Markers live inside the viewport, so they **scale with zoom** (the requested behavior) and stay anchored. Available to **all viewers**; the DM placement-click + pin-drag are guarded by element existence and coexist (pan bails on a pin / while placing; pin-drag `stopPropagation`s).
  - **Grid overlay (persisted, migration 56).** Optional square tactical grid: `grid_enabled` + `grid_size`/`grid_offset_x`/`_y` (all in **source-image pixels**) + `grid_color`/`grid_opacity`, edited on the map form (the `grid_present` hidden field lets `_clean` coerce the checkbox; colour hex-validated, size ≥ 2, opacity 0–100). Drawn client-side into a `<canvas>` whose buffer = the image's `naturalWidth×naturalHeight` and is stretched to the image box, so **cells stay square and content-aligned at any display size or zoom** (and scale with the viewport transform). Visible to players when enabled. *Still future: monsters as marker targets, editing a marker's target in place, a default grid-size auto-detect.*

## Phase 12 — Player-controlled companions & summons

Owner wants **one PC per player to stay strict**, but to let players **control extra creatures**: DM-granted **NPC companions** and **summons**. A companion/summon is just another *creature* (reuses the Phase-5 engine); the new piece is a **looser "controls" relationship** distinct from the strict PC link.

- **12a — The control relationship (migration 51).** A `controlled_by` column (controlling user's id, 0 = none; no FK — orphan resolves as "none" on read). A user controls **many** creatures; each creature has **at most one** controller; `users.creature_id` stays untouched, so "one PC per player" holds. `list_controlled_by`/`set_controlled_by`/`clear_control_for_user` (setter written only via its own DM-gated path). **The gates extend:** `_controls_creature` + `can_view_creature`/`can_edit_creature` pass for a controlled creature — so a player can view + fully edit a companion's sheet **even a `visibility='hidden'` NPC**, while still 404ing on others. **The DM grants control** via a "Controlled by player" `<select>` on the edit form (DM-only). The sheet shows a **🎮 Your companions** panel + a "controlled by <player>" header badge. Deleting a user **releases** their companions. *Limitation: a player can't add loot/gear to a companion (NPC gear-add is the DM's loot form) — the DM equips companions.*
- **12b — Summons (migration 52).** A bundled catalog `data/summons.json` (SRD 5.1 beasts/familiars, paraphrased — Owl/Cat familiars, Wolf, Black Bear, Giant Spider, Skeleton) + `models/summons.py`. A player **spawns** one from a picker on **their own PC sheet** (`can_summon` = the sheet is the viewer's `_my_pc_id`) → `spawn(slug, user_id)` copies the stat block into a new creature, sets `controlled_by = self`, flags **`is_summon=1`**. Rides the 12a control spine (others 404 since `kind='monster'`); **excluded from the Bestiary** (`list_monsters` gets `AND is_summon = 0`). The Companions panel tags summons **✨ summon** + a **✕ Dismiss** (`/summon/<id>/dismiss` → delete; guarded to controller/DM, 404s on a non-summon). `summon_new` is player-accessible (not DM-only). *Still future: summons into the combat tracker, duration/concentration, a DM allow-list.*

- **Later / optional — Session scheduling.** Owner wants this near the end. Optional AI assists (NPC generation, session summaries) also slot here.
- **Phase 11 — Ambient/media embeds. DECIDED AGAINST (2026-06-09).** A nested YouTube/MP3 player for background music. Shelved: ambient audio is better solved *outside* the app (a speaker + Spotify/YouTube, a Discord bot, Tabletop Audio/Syrinscape) — no autoplay fights, and crucially **no re-buffer on navigation** (this app does full-page reloads, so any in-page player stutters on every tab change). The one version that might justify itself — tying a suggested track to a **location** — is still marginal. Non-goal unless that angle becomes compelling. (Tech notes if revisited: YouTube IFrame API; autoplay blocked unless muted; CSP `frame-src` must allow `youtube-nocookie.com`.)
- **Phase 13 (idea, not committed) — Blank-slate / homebrew mode (DM-editable content).** Ship the **whole skeleton with none of the content baked in** — engine/tabs/sheets/combat/visibility/dice present, but classes/feats/spells/items/actions start **empty and user-authored**. Also the clean, **SRD/PHB-free distributable**.
  - **Why it fits:** the app already splits a **system-agnostic engine** (the two spines + dice/combat/inventory) from a **5e content layer** in read-only `data/*.json` catalogs. Per-creature **custom-add already exists** for feats/actions/items/spells — blank mode generalizes that to "author the catalog itself."
  - **Core lift — editable, DB-backed catalogs.** Promote the JSON catalogs to a content layer the DM can CRUD at runtime (new `content_*` tables or a generic `content(kind, slug, json)` store), with `data/*.json` becoming an optional seed/import. Resolve a catalog as *DB entries (+ optional bundled pack)*, so DM-added content shows up in the same pickers. The `classes.json` shape becomes a class builder form; spells/feats/items get the same.
  - **Delivery (two options, not exclusive):** (1) a `system`/content-pack setting in `meta` (`'srd-5e'` = bundled pack loads, `'blank'` = empty); (2) a separate instance — `DND_DB_PATH=homebrew.db` already gives an isolated DB; pair with empty catalogs for a parallel "blank" site, zero code change.
  - **Content packs:** once catalogs are data, "the SRD" is just one importable/exportable pack; homebrew becomes shareable. The CC-BY SRD pack ships; PHB-derived packs stay user-supplied.
  - **Stretch (probably never): full system-agnostic.** The engine hard-codes 5e (six ability scores, `floor((score-10)/2)`, d20, AC/HP, `2+(level-1)//4`, hit dice, Vancian slots). Truly system-neutral would parameterize those. **Recommended first cut:** keep the 5e engine, make only the **content** blank/editable — ~90% of the ask for a fraction of the work.
- **Phase 14 (idea, post-launch) — Multiclassing.** Owner's call: **skip for now, revisit after launch.** Let one creature hold **multiple class levels** instead of a single `class_name`. The **most invasive change to the class spine** — nearly every per-class computation assumes one class.
  - **Data model:** replace/supplement single `class_name`/`subclass`/`level` with a **`creature_classes` join** (creature_id, class slug, subclass, levels), keeping `level` as derived **total character level**. Migration + back-fill.
  - **Recompute per class then combine:** features/resources/class-actions/scaling iterate each class at its own level (mostly works — keyed by slug+level). **Proficiency bonus** uses *total* level. **Saves:** only the **first class** grants save proficiencies. **Armor/weapon/skill proficiencies:** union, with multiclass limited-proficiency rules. **HP:** per-class hit die per level.
  - **Spell slots — the gnarly bit:** 5e uses a **combined caster level** (full +full, half +half, ⅓ for EK/AT, Warlock pact slots separate), then one shared slot table. `models/spellcasting` needs a multiclass slot path; spells known/prepared stay per-class; casting stat/DC per-class.
  - **UI:** picking a *new* class mid-career (no fresh kit; prerequisites), and a level-up flow that asks **which class**.
  - **Why last:** touches `models/classes`, `creature`, `proficiency`, `spellcasting`, `resources`, `actions`, the form, and the header — best done once the single-class systems are stable (they now are) and after launch. The heaviest single item in the plan.
