# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **D&D campaign tracker** — a personal tool for the project owner, who is the **Dungeon Master (DM)**, with a **website** his players log into to track their own characters. Built phase-by-phase as both a real tool and a tech-learning project (the natural "next level up" from the sibling `stock-tracker` and `cloud-habit-tracker` projects: this one is the first genuinely **multi-user, authenticated, hosted web app** in the workspace).

The owner and his players are **new to D&D**, so the app doubles as a way to *learn the game*: it surfaces rules text (spell/ability descriptions, dice) inline so the table doesn't need to memorize the rulebook.

**Posture:** mostly **track** (record-keeping), with targeted **assist** features (dice roller, combat math, rules lookup) where they clearly earn their place.

## Roles & audience

- **DM (owner)** = admin. Sees and edits the entire campaign world, including hidden/secret entities the players don't know about.
- **Players (friends)** = each logs in, sees only their own character and the things they've discovered or the DM has shared.

## The two architectural spines

Everything in this app hangs off two core ideas. Get these right and the features are mostly views on top.

### 1. The creature / stat-block engine

A **player character, an NPC, and a monster are the same kind of thing**: a *creature* with a stat block (six ability scores, HP, AC, resistances/immunities, conditions, abilities). Model this **once**. The `kind` column ('pc' | 'npc' | 'monster') is the only thing that distinguishes them — a tavern keeper is just a low-stat NPC. Two world-flavor traits also live on every creature (migration 2):

- **`disposition`** — a 5-point spectrum, hate→love: 'hostile' | 'unfriendly' | 'neutral' | 'friendly' | 'allied'. How the creature treats the party. The DM can flip it **live** from the creature's page (a friendly merchant turning hostile mid-scene), not just via the edit form. Surfaced for NPCs/monsters.
- **`alignment`** ('' | LG..CE) — the creature's moral compass. A separate, more granular axis from disposition; applies to anyone, including PCs.

- A **character sheet** = the full, editable creature view (player-owned).
- The **monster inspector** (Baldur's Gate 3-style "inspect") = a trimmed, read-only creature view.
- **Combat tracking** operates on creatures generically, so it works for PCs and monsters with no special-casing.

### 2. The public/private visibility spine ("fog of war")

Every **entity** (NPC, location, map marker, monster, even individual monster stats and abilities) carries a **visibility state** per viewer:

- The **DM sees everything.**
- **Players see only what they've discovered** (invisible / partially-known / fully-known).

This is **not one feature** — it's a rule the character sheets, monster inspector, map overlays, campaign blog, and entity sidebar all enforce. **Bake a `visibility` concept into the data model from Phase 1**, even while the app is still single-user (DM-only). Real enforcement against player logins arrives in the auth phase, but the schema must anticipate it from the start.

## Shared "entity" concept

The **sidebar list of known things**, the **map markers**, and the **things mentioned in the campaign blog** all point at the *same underlying entities* (NPCs, locations, factions, items). Model entities **once** and surface them in multiple views — do not build three parallel lists.

## Tech decisions

- **Language / framework:** Python + **Flask** (continuity with `stock-tracker`; owner already knows the patterns).
- **Storage:** **SQLite** (stdlib `sqlite3`) to start, same as stock-tracker Phase 3+. Revisit only if hosting demands it.
- **Frontend:** server-rendered templates + light JS. Keep it simple early; the interactive map (late phase) is the one place that needs real client-side canvas work.
- **Rules data source:** D&D 5e **SRD** content, available under **CC-BY-4.0** (System Reference Document 5.1). Pull spell/ability/monster reference data from an open SRD source (e.g. Open5e / the 5e-SRD API), bundled locally where practical. **Attribute per CC-BY.** The SRD does not cover *every* official spell/monster (some are in paid books) — design so custom entries can be hand-added.
- **Privacy:** DM secrets and hidden entities must never leak to the player-facing API/templates. Treat visibility as a server-side filter, never a client-side hide.
- **AI (optional, later):** the workspace already has Claude API patterns (`stock-tracker`). Possible assist uses — generating an NPC, summarizing a session — are explicitly *late / optional*, not core.

**Magic items (migrations 19–20).** An equipped item can grant an **AC bonus**, **ability-score bonuses** (`stat_bonuses`, stored as `ability:amount` pairs), and/or **spells** (`grants_spells` slugs). These are applied by **computing** the creature's *effective* AC / ability scores / spell list from its equipped items (`effective_ac`, `effective_abilities`, `effective_spells`) — the base sheet is never mutated, so bonuses revert automatically on unequip/remove. The sheet shows effective values with a small `+N` tag and item-granted spells flagged "from <item>" (read-only); combat snapshots effective AC + DEX. **Body armor (migration 21)** follows 5e rules — `armor_type` (light/medium/heavy) + `armor_base` **set** the AC and cap how much DEX applies (light = full, medium = +2, heavy = none); `effective_ac` uses the worn armor's base + capped DEX; an **unarmored PC** is `10 + DEX` with optional **Unarmored Defense** (migration 22 `unarmored_defense`: barbarian +CON, monk +WIS); **NPCs/monsters keep their manual natural AC**; then additive `ac_bonus` (shield/ring/enhancement) stacks on top. (Armor with no base AC is ignored, never zeroes AC.) AC shows everywhere via the `eff_ac` filter with an `ac_breakdown` tooltip.

**Class system (the bones).** `data/classes.json` + `models/classes.py` define the 12 SRD classes (hit die, primary/save abilities, Unarmored Defense, spell ability, recommended stat array, starting equipment, gold). A creature records `class_name` (migration 23). Picking a class on the character form applies a **BG3-style starting kit** (`_apply_class` with `starting_kit`): recommended stats, **level-1 HP from the hit die + CON**, starting gold, and **auto-equipped starting gear** (which feeds the AC/armor system) — plus it sets Unarmored Defense (barbarian/monk). Player self-create always applies the kit; the DM form has an "Apply starting kit" checkbox. **Leveling ties in:** the level-up control pre-fills HP with the **fixed hit-die average + CON** (`hit_die_average`); the class shows on the sheet ("Level 5 Barbarian"). Each class in `classes.json` carries its SRD `skill_count` + allowed `skills` list (drives the guided skill picker) and a per-level `features` list.

**Class features (display layer).** Every class in `classes.json` has a `features` list of `{level, name, description}` entries — the SRD class features L1–20 (Rage, Sneak Attack, Second Wind, Spellcasting…, with Ability Score Improvement markers and a generic subclass marker at the subclass level; subclass-specific feature trees are still future). `models/classes.py` exposes `class_features(slug, level)` (everything unlocked through the creature's level) and `class_features_remaining(slug, level)` (a "Coming up" preview) — both **computed on read**, never stored, mirroring effective AC/abilities. The sheet renders a **"<Class> Features"** section (between Skills and gear, only for classed creatures) listing unlocked features by level with a level chip + description (dice in the text are mode-aware rollable via `dicetext`), plus a collapsible **"Coming up"** showing the next few.

**Auto-granted class actions (migration 26).** The action-type features — those tagged with a `category` (+ optional `dice`) in `classes.json` (Rage, Second Wind, Sneak Attack, Channel Divinity, Cunning Action…; casters mostly get none since their kit is spells) — are **auto-granted into the creature's actions list** so they're usable in combat, not just reference. `creature_actions` gained a `source` column ('' = hand-added/action-book grab, 'class' = auto-granted). `models/actions.grant_class_actions(creature_id, slug, level)` **reconciles** (not wipes) the creature's class-sourced actions: keep the still-desired ones (preserving each one's `hidden` flag + any edits), drop the no-longer-granted ones, add the newly unlocked ones (via `grantable_class_features`) — idempotent, leaves hand-added actions untouched. The app helper `_sync_class_actions(creature_id)` (reads the creature fresh) runs after **class apply** (`_apply_class`), **character edit**, and **level-up**, so class actions always match the current class + level; class change swaps them cleanly. Granted actions show a small gold **"class"** tag in `_actions.html`, and (since a real delete would just re-sync back) carry a **Hide** control instead of the **×** — non-action passives like ASI/Spellcasting stay display-only in the features section. *Still future:* subclass features, scaling dice (Sneak Attack die count, Second Wind +level), and applying feature *mechanics* beyond the roll.

**Hide / Show hidden on the sheet's filterable lists (migration 27).** Spells, actions, and inventory each gained a per-entry **Hide** toggle and a **"Show hidden (N)"** button in their filter bar — a persistent soft-delete / declutter. `hidden` columns on `creature_spells` / `creature_actions` / `creature_items`; setters `set_spell_hidden` / `set_action_hidden` / `set_item_hidden`; routes `/spellbook/hidden`, `/actions/<id>/hidden`, `/inventory/<id>/hidden` (edit-gated, AJAX-rerender the `#spells`/`#actions`/`#gear` fragment). Hidden rows carry `data-hidden="1"`; the existing client-side filter JS adds a `showHidden` predicate (default off) so they're filtered out unless toggled, then shown dimmed (`.is-hidden`). This is also the **permanent way to remove an auto-granted class action** — the reconcile sync preserves the `hidden` flag, so a hidden Rage stays hidden through level-ups. (Item-granted spells, having no DB row, can't be hidden.)

### Class system depth (roadmap)

With the class *bones* in place (data model, starting kits, hit-die leveling, features display, auto-granted class actions, proficiency, spellcasting), this roadmap fills in the mechanics that make a class feel complete. Worked through in value-per-effort order; each item layers on the existing computed-on-read + reconcile patterns rather than mutating the sheet.

- [x] **Subclasses (migration 28).** Each class records a `subclass` slug; `classes.json` carries `subclass_level` + `subclass_label` (Primal Path, Divine Domain, …) and a `subclasses` list, each with its own level-keyed `features` (SRD: one archetype per class — Berserker, Lore, Life, Land, Champion, Open Hand, Devotion, Hunter, Thief, Draconic, Fiend, Evocation). `class_features`/`class_features_remaining`/`grantable_class_features` take an optional `subclass` and **merge** the subclass's features into the class list (sorted by level, tagged `subclass`); so subclass features show in the **<Class> Features** section (with a small subclass pill) and their action-type entries (Cutting Words, Preserve Life, Fast Hands…) **auto-grant into the actions list** through the same `grant_class_actions` reconcile. The character form gains a **subclass `<select>`** (filtered to the chosen class via JS, like the skill picker); server validates the pick belongs to the class (else clears it). Changing class clears an incompatible subclass.
- [x] **Class resources (migration 29, `models/resources.py`).** Limited-use, rest-recharged pools — the non-spell cousin of the slot tracker. Each class carries a `resources` list in `classes.json` (Rage, Ki, Channel Divinity, Lay on Hands, Action Surge/Second Wind/Indomitable, Wild Shape, Bardic Inspiration, Sorcery Points, Divine Sense), each with a computed `max` (`fixed`/`level`/`level_times`/`steps`(-1 = ∞)/`ability_mod`), an optional `min_level`, and a `recharge` (`short` = short OR long; `long` = long only; optional `short_from_level` for Bard Font of Inspiration). **Max is computed on read; only the expended amount is stored** (`creature_resources`, mirrors `creature_spell_slots`). `resource_rows` builds the display rows; `spend_resource`/`restore_resource` (amount-aware for pools); `rest(creature, kind)` clears the matching keys. The sheet shows a **Class Resources panel** (`_resources.html`, `#resources` fragment) — pips for small pools, a numeric `available/total` + amount control for HP/point **pools** (Lay on Hands), ∞ for unlimited — with −/+ spend/restore (AJAX) and **Short/Short rest** buttons. Rests recharge **resources *and* spell slots** together, so a non-caster gets a rest button too; to avoid a duplicate, the spellcasting panel hides its own rests when a resources panel is present (`has_resources`). Resource recharge is also wired into the **Party-tab rests** (DM, all PCs). Edit-gated like the spellbook (`_require_edit_form_creature`), so a player manages only their own PC. *Still future:* spending Ki/slots on specific options, sorcery-point↔slot conversion, applying the mechanical effect beyond the counter.
- [x] **Scaling feature numbers.** A feature can carry a `scale` spec in `classes.json` that recomputes its `dice` by level: `dice_count` (Sneak Attack = ceil(level/2)d6; Divine Strike 1d8→2d8 via a steps table), `die_steps` (Martial Arts 1d4→1d10; Bardic Inspiration / Cutting Words 1d6→1d12), `dice_plus_level` (Second Wind 1d10+level). `models/classes._scaled_dice`/`_apply_scaling` apply it in `class_features` (computed on read), so the **Class Features** section shows the level-correct dice (rollable in assist mode), and `grant_class_actions` **rescales the dice on kept class actions** during its reconcile — so leveling a Rogue bumps the granted Sneak Attack 1d6→3d6 while preserving its `hidden` flag. (Rage's flat damage bonus stays descriptive; uses-counts are the [class resources] layer, not dice.)
- [ ] **Hit dice as a resource.** Track a per-creature hit-dice pool (class hit die × level); real short-rest spending instead of the Party tab's "half missing HP" fudge. *(Skipped for now — owner is happy with the Party tab's half-missing-HP short rest; revisit only if the table wants real hit-dice bookkeeping.)*
- [x] **ASI / feats (migration 30, `models/asi.py`).** The +2/+1 ability bumps a class grants at its ASI levels (4/8/12/16/19, plus Fighter 6/14 & Rogue 10 — the "Ability Score Improvement" entries already in `classes.json`'s `features`). The **budget** is computed on read (`asi_slots` counts those features ≤ level, ×2 points); only the **allocation** is stored (`creature_asi`: `ability`+`bonus`). **`effective_abilities` folds the bumps in on read** (alongside item `stat_bonuses`), so the base sheet is never mutated and *everything derived* — AC, modifiers, saves, skills, spell attack/DC — ripples automatically (`_ability_with_items` adds ASI too). The sheet shows an **Ability Score Improvements** panel (`_asi.html`, between the ability grid and defenses, only when ≥1 slot is earned) with a per-ability −/+ stepper and a live "N of M points left" budget; the `+` disables at 0 remaining or a base+ASI of 20 (the cap). Edit-gated to owner/DM (`_require_edit_form_creature`); `/asi/adjust` is a **full redirect** (not an AJAX fragment) since a bump touches numbers all over the sheet. `effective_abilities` now returns `{score, bonus(items), asi, base}` so the panel can show the breakdown. *Still future: hard validation that base+ASI ≤ 20 against a DM manually raising the base score after allocating (the allocator caps, a raw base edit can still exceed it).*

  - **Feats (skeleton — migration 31, `models/feats.py`).** A tracked list of feats per creature (display only — **no mechanical effects yet**), since a character may take a feat *instead* of an ASI (the two aren't budget-linked yet). Mirrors the action book: a premade catalog (`data/feats.json`) grabbed onto the creature (copied into `creature_feats`: name/description/prerequisite) plus a hand-added custom feat; AJAX `#feats` fragment (add/remove) with a `/feats/add` + `/feats/<id>/remove` pair, edit-gated. Shows as a **Feats** section on the sheet (after Class Features). The ASI panel links to it ("take a feat instead"). **Licensing:** only **Grappler** is from the SRD (CC-BY-4.0, attributed in the JSON); the rest of the catalog carries **original paraphrased** one-line summaries (game *mechanics* aren't copyrightable, only the exact PHB wording) — the PHB itself is **not** redistributable, so we can't bundle its feat/class text verbatim. Custom-add covers anything missing. *Still future: linking a feat choice to the ASI budget, and applying feat mechanics (the +1 ability bumps several feats grant, proficiencies, reactions, etc.).*
- [x] **Spells known / prepared limits (no migration — computed on read).** Per-class spell-count caps shown on the Spellcasting panel. Two caster models, driven by a new `prepared_caster` flag in `classes.json`: **known casters** (Bard/Sorcerer/Ranger/Warlock) have a per-level `spells_known` table; **prepared casters** (Cleric/Druid/Wizard/Paladin) compute prepared = spell-ability mod + caster level (full) or half level (Paladin), min 1. Every caster also has a per-level `cantrips_known` cap (Paladin/Ranger have none). `models/spellcasting.spell_limits(creature, eff_abilities)` returns `{mode, cantrips{count,max}|None, leveled{count,max,label}}`, counting from the creature's **own spellbook** (`creature_spells` — item-granted spells don't count); folded into `_spellcasting_ctx` so the sheet + `#spells` AJAX fragment both show it. The panel renders **Cantrips N/M** and **Known/Prepared N/M** with an amber **"over limit"** flag when exceeded. **Guided, not enforced** (mirrors the skill picker): going over still works — multiclass / background / feat / item spell sources aren't modeled, so a hard block would misfire. The `spells_known`/`cantrips_known` tables are SRD 5e values in `classes.json`. *Still future: hard enforcement, Wizard spellbook size (tracked separately from prepared), and subclass casters (Eldritch Knight / Arcane Trickster — base class is `caster_type:none`).*
- [x] **Weapon & armor proficiency (no migration — computed on read).** Per-class `armor_prof` (light/medium/heavy/shields) + `weapon_prof` (simple/martial/named) added to all 12 classes in `classes.json`. `models/proficiency.py` exposes `armor_proficiencies` / `weapon_proficiencies` / `proficiency_summary` (a **Proficiencies** section on the sheet, after Skills) and **`armor_proficiency_issue(creature)`** — the **"Wizard in plate" rule**: if a classed creature wears body armor (matched via the equipped armor's `armor_type`) its class isn't proficient with, it flags **⚠ not proficient** beside AC and a red **"Can't cast"** block in the Spellcasting panel (5e: non-proficient armor → disadvantage on STR/DEX d20s + no casting). Threaded through `_spellcasting_ctx` (`armor_block`) so the `#spells` fragment shows it too. **Guided, not enforced** — the rolls/casts aren't actually blocked, just flagged (no weapon-attack roll exists yet to consume the weapon-proficiency bonus, so weapon prof is **display + ready-to-feed**; only **body armor** is auto-checked — shields have no reliable item flag). *Still future: a real weapon-attack roll (d20 + ability + prof) that consumes weapon proficiency; shield-proficiency check; actually applying disadvantage/cast-block.* Also (UI): the sheet's spell list now shows an **unprepared *leveled*** spell's badge in **red** (clearer "can't cast now" than the old grey); cantrips stay neutral since they're always castable (`.spell-line[data-cantrip="0"] .prep-toggle:not(.on)`).
- [x] **Expertise / half-proficiency (migration 32).** **Expertise** = double proficiency on a chosen *proficient* skill (Rogue/Bard). Stored as an `expertise` flag on the `creature_skills` row (so it always implies proficiency); `expertise_skills(creature_id)` reads it, `set_skill_proficiencies(creature_id, slugs, expertise_slugs)` writes both (expertise filtered to the proficient set). The DM-only edit-form skill picker gained a per-skill **✦ exp** checkbox, gated by JS to enable only when the skill is proficient. **Half-proficiency** is computed (not stored) from class/subclass features via `_has_feature`: **Jack of All Trades** (Bard 2+) adds half PB *rounded down* to any non-proficient skill; **Remarkable Athlete** (Champion fighter 7+) adds half PB *rounded up* to non-proficient STR/DEX/CON skills. `skill_table` now returns a `tier` ('expertise'|'proficient'|'half'|None) and folds the right bonus into each modifier (2×PB / PB / half PB); the sheet's Skills section shows tier dots (◉ expertise, ● proficient, ◐ half, ○ none) + an "expertise" flag, and the legend explains them. Glossary: `expertise`, `half-proficiency`. *Still future: expertise on tools/thieves' tools; JoAT/Remarkable Athlete on **raw ability-check** buttons + initiative (currently skills only); hard skill-count enforcement.*
- [ ] **Multiclassing.** *Deferred to **post-launch** (owner's call) — see [Phase 14] below.* Multiple class levels per creature; multiclass proficiency-bonus (total level) and the multiclass caster-slot formula. The most invasive change to the class spine (every per-class computation — features, resources, slots, proficiencies, saves — assumes one `class_name`), so it's intentionally held until the app is built out and launched.

The tracker shows a death-save row for a downed PC — success/failure pips, a **🎲 Save** roll button + manual +✓/+✕, and a Stabilized/💀 Dead status (monsters at 0 just drop, no saves). Glossary: `death-save`. *Still future: massive-damage instant death (single hit ≥ max HP), auto-failure on a crit hit while down, and logging the save to the shared dice log.*

### Magic items & combat depth (roadmap)

A 5e-fundamentals review (this session) found the character build deep but spotted gaps in **magic-item balance** and in **applying stored data during combat**. Worked in value-per-effort order; each reuses the computed-on-read + snapshot-on-add patterns. All **guided, not enforced** unless noted.

- [x] **Attunement (migration 41).** 5e's soft cap on powerful items: a creature attunes to at most **3** items, and only items flagged **Requires Attunement** count (a +1 sword, Bag of Holding, etc. stack freely). `attunement_required` is a real flag now (on `items.json` + the `loot_items`/`creature_items` columns, carried through give/take/drop like `stat_bonuses`); `attuned` is a per-item toggle on `creature_items`. **Strict mode (owner's call):** an attunement-requiring item's bonuses (`ac_bonus`/`stat_bonuses`/`grants_spells`) apply **only when attuned** — `equipped_ac_bonus`/`equipped_stat_bonuses`/`equipped_granted_spells` gain `AND (attunement_required = 0 OR attuned = 1)` (shared `_ATTUNED_OK`), so a worn-but-unattuned magic item lies dormant (correct 5e; magic armor's base AC still works since that's `armor_base`, not a magic bonus). `models/inventory.set_attuned`/`attunement_summary` (count/cap/over/any); the gear panel shows an **✨ Attunement N/3** counter (amber + ⚠ when over `ATTUNEMENT_CAP`=3 — over-3 still works), each attunement-item line shows a *needs attunement* / *✨ attuned* badge + an **Attune/Unattune** toggle (`/inventory/<id>/attune`, edit-gated, AJAX `#gear` rerender). The DM item-creation form (`magic_fields`) gained a **Requires attunement** checkbox. *Still future: attunement requiring a short rest, class/race-restricted attunement.*
- [x] **Damage resistance / vulnerability / immunity in combat (migration 42).** The defenses stored on every creature since migration 1 (shown on the sheet) finally apply where they matter: dealing damage in the tracker. Combatants **snapshot their `resistances`/`immunities`/`vulnerabilities` on add** (like AC/HP/speed) into new `combatants` columns. The damage control gains a **damage-type `<select>`** (the 13 5e types, `DAMAGE_TYPES`) — shown only when the combatant *has* defenses; `combat.damage_multiplier` matches the type word-wise against the snapshot (immune → 0×, resisted → ½ rounded down, vulnerable → 2×; resist+vuln cancel, immunity wins) and `apply_hp(combatant_id, delta, damage_type)` applies it **before temp-HP absorption**, returning `{raw, applied, label, damage_type}`. The route flashes the adjustment ("10 fire → 5 (resisted).") and bases the **concentration save DC on the *applied* damage**. Each combatant line shows ∅/½/2× defense tags. Leaving the type blank (or an undefended type) deals flat damage as before. *Still future: conditional resistance (Rage = physical), "nonmagical/nonsilvered" qualifiers (a word match treats "nonmagical bludgeoning" as plain bludgeoning resistance).*
- [x] **Heroic Inspiration (migration 43).** The universal advantage token (distinct from *Bardic* Inspiration, a class resource). A single `inspiration` boolean on creatures (`models/creature.set_inspiration`); the **Character sheet's vitals** show an **✨ Inspiration** tile for PCs with a **Grant/Use** toggle (`/character/<id>/inspiration`, edit-gated to owner/DM — the DM grants, the owner spends). Glossary: `inspiration`. *Still future: once adv/dis is on the roll buttons, wire "Use" to actually roll one d20 with advantage instead of just clearing the flag.*
- [x] **Advantage / disadvantage from the sheet (no migration).** The dice engine already parses `d20 adv`/`dis` (Phase 2); now surfaced where rolls happen. A **shared Normal / Advantage / Disadvantage selector** sits above the ability grid (one control, not one per roll — avoids cluttering ~25 buttons); a capture-phase submit listener appends ` adv`/` dis` to a roll's `expression` just before it POSTs to `dice_roll`, but **only for single d20 rolls** (`/^1?d20([+-]\d+)?$/` — checks, saves, skills, weapon **and** spell attacks; never damage dice). - [x] **Critical hits (no migration).** A nat 20 doubles the damage dice. `weapon_attacks` now returns a **`crit`** expression alongside `damage` — `models/weapons._double_dice` doubles each dice term's count (`2d6` → `4d6`) while keeping the flat ability mod (5e: roll the dice twice, don't double the modifier). The sheet's **Attacks** section gained a **💥 Crit** roll button (assist mode) next to Damage, and a static "crit NdM" stat in track mode. *Still future: spell-damage crits (spell damage lives in freeform description text, not a built expression), crit in the combat tracker, Brutal Critical / Savage Attacks extra dice, auto-crit vs. a paralyzed/unconscious target.*
- [x] **Challenge Rating + encounter difficulty (migration 44).** A `cr` **float** column on creatures (0, 1/8 … 30; `_FLOAT_FIELDS` in `_clean` coerces the form value). `models/creature.py` carries the DMG **CR→XP table** (`CR_XP`) + `cr_label` ("0.25"→"1/4"), `cr_xp`, `CR_CHOICES` (form picker), and a **`cr` Jinja filter**. CR shows in the **monster sheet header** ("CR 1/4" instead of "Level N") and as a masked **Challenge** vital in the inspector; the character form gained a **CR `<select>`**. `models/encounters.py` adds the **difficulty calculator**: `encounter_multiplier` (DMG count multiplier 1×→4×), `party_thresholds` (per-level easy/med/hard/deadly table summed over the PC party), and `encounter_difficulty(members, party)` → `{raw_xp, adjusted_xp, count, multiplier, thresholds, party_size, rating}` (Trivial/Easy/Medium/Hard/Deadly, or None with no party). `encounter_members` now selects `c.cr`; the **encounter detail page** shows a colored rating badge + the XP math + the party budget, and per-member CR. Advisory only. *Still future: the party-size column shift (party not 3–5 bumps the multiplier), a hypothetical-party input (currently reads the live PC roster), and per-encounter notes.*

**Spellcasting (migration 25, `models/spellcasting.py`).** Two computed layers on the spellbook. **Stats:** a caster's **spell attack bonus** (`proficiency bonus + ability mod`) and **save DC** (`8 + proficiency bonus + ability mod`), where the ability is the class's `spell_ability` (data already present) — no storage, computed on read. **Slots:** leveled spells spend a slot of their level (cantrips are free); a creature's *max* slots come from its **caster type** (new `caster_type` in `classes.json`: `full` Bard/Cleric/Druid/Sorcerer/Wizard, `half` Paladin/Ranger, `pact` Warlock, `none`) + level via the 5e tables (`_FULL`/`_HALF`/`_PACT`); only *expended* slots are stored (`creature_spell_slots`). A **long rest** clears all slots, a **short rest** recharges only Warlock pact slots — wired into both the **Party-tab rests** (DM, all PCs) and per-caster **rest buttons on the sheet**. The sheet's spell section gained a **Spellcasting panel** (ability · attack · DC + a slot tracker with pip display and ±/spend/restore controls), and each spell line gains an **Attack** roll (assist mode) using the spell attack bonus, a **DC** badge for save spells, and a **Cast ▸** button that spends a slot of the spell's level (disabled when none left). Slot/rest mutations are edit-gated (`/spellbook/slot`, `/spellbook/rest` via `_require_edit_form_creature`, so a player manages only their own PC) and re-render the `#spells` fragment via AJAX. *Still future:* upcasting (spend a higher slot), per-class known/prepared limits, ritual casting, concentration tracking.

**Proficiency layer (migration 24).** The trained-bonus system on saves and skills (`models/proficiency.py`). `creature.proficiency_bonus(level)` = `2 + (level-1)//4` (+2 at 1–4 … +6 at 17–20). **Saving throws:** proficiency is *derived from the class* (each grants two, already in `classes.json`'s `saves`) — no per-creature storage; `save_table` returns each ability's save modifier (mod + prof when proficient). **Skill checks:** the 18 SRD skills (`SKILLS`, slug→ability) with per-creature proficiency stored in the `creature_skills` join (set on the character form's **DM-only** "Skill Proficiencies" picker via `set_skill_proficiencies`); `skill_table` returns each skill's modifier. **Skills are DM-controlled** — the picker is hidden from players and `set_skill_proficiencies` is gated by `is_dm()` in `character_edit` (players can still edit their own PC's other stats per 7c, but a crafted POST can't reset skills); a self-created player PC starts with none until the DM assigns them. Both are **computed on read** (never baked into the sheet), mirroring effective AC/abilities. The sheet's ability grid gains a **Save** button (beside Check) with a proficiency dot, and a new **Skills** section with per-skill Roll buttons — all posting `d20 + (modifier incl. prof)` through the existing dice engine (no engine change); the `signed` filter formats the computed modifier into the expression. Glossary terms added (proficiency, proficiency-bonus, skill, saving-throw-prof). The skill picker is a **guided (not enforced)** chooser: each class in `classes.json` now carries its SRD `skill_count` + allowed `skills` list (Bard = any), and inline JS on the form highlights the selected class's skills, tags each option class/off-list, and shows a live "X of N class skills" budget (amber when over) — updating when the class select changes. Guidance only: off-list picks still work (background/race/feat skill sources aren't modeled) and `set_skill_proficiencies` stays unlimited. *Still future:* hard enforcement, expertise/half-proficiency, and weapon/save proficiency for attack rolls.

DM item-creation forms (loot create + NPC gear) get a `magic_fields()` section (AC bonus, 6 stat bonuses, spell multi-select); premade magic items live in `items.json` (Shield +2 AC, Cloak/Ring of Protection +1, Amulet of Health CON+2, Belt of Giant Strength STR+2, Wand of Fire Bolt). Bonuses carry through loot give/take/drop. **Bestiary is now player-readable with a two-level monster fog of war** (`can_inspect_monster`): **level 1** = the DM toggles each monster's `visibility` (Show/Hide to players) — players' bestiary lists only *visible* monsters and 404s on hidden ones; **level 2** = the DM toggles `stats_revealed` (from the inspector) — a visible-but-unrevealed monster shows a masked card (🔒) + masked inspector (`?`), and reveal shows the stat block. Players get the **inspector only** (the full monster sheet stays DM-only); the DM gets both toggles (on the card and the inspector) + encounters/create.

## Conventions

- **Two spines first.** When adding any feature, ask: does it reuse the creature engine? does it respect visibility? Don't fork either.
- **Visibility is server-side.** Never ship DM-hidden data to the client and hide it with CSS/JS.
- **SRD attribution.** Anything sourced from the 5e SRD must carry CC-BY-4.0 attribution.
- **DM data vs player data** stay clearly separated in queries; default a query to the *least* privileged view and widen for the DM, not the reverse.
- **No build step** unless a phase truly needs one (likely only the map).
- **Commits / PRs: no AI attribution.** Do **not** add a `Co-Authored-By: Claude …` trailer, a "Generated with Claude Code" line, or otherwise list Claude/AI as a contributor on commits or pull requests. Keep commit messages plain.

## D&D glossary (for the owner — and future sessions)

- **DM (Dungeon Master)** — runs the game and the world; the admin role here.
- **PC** — player character. **NPC** — non-player character (run by the DM).
- **Ability scores** — STR, DEX, CON, INT, WIS, CHA. Most numbers derive from these via a **modifier**.
- **Check / saving throw** — `d20 + modifier` vs a **DC** (Difficulty Class). Check = attempt something; save = resist something.
- **AC (Armor Class)** — how hard a creature is to hit. **HP (Hit Points)** — health.
- **Initiative** — turn order in combat (`d20 + DEX modifier`).
- **Condition** — status effect (poisoned, prone, stunned, frightened, unconscious, …).
- **Spell slot** — a consumable resource for casting; refreshes on a **long rest**.
- **Short rest / long rest** — recovery mechanics that restore HP / resources.
- **Encounter** — a prepared set of monsters for a fight.
- **Stat block** — the bundle of a creature's combat-relevant numbers.
- **SRD** — System Reference Document; the openly-licensed (CC-BY-4.0) subset of D&D 5e rules we draw reference text from.
- **dNN notation** — `d20` = roll a 20-sided die; `2d6+3` = roll two d6 and add 3.
